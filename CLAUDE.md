# Working on cauriflores.com

Cauri's site: writing at the root, and the apps under it. Static, served by
GitHub Pages from this repo (`github.com/cauriflores/web`) on a custom domain.
Live at **https://cauriflores.com/**.

Plain HTML and CSS generated by one Python script. No framework, no Jekyll,
no CI.

## Build

```bash
python3 tools/build-blog.py   # then commit the generated files
```

It reads `src/posts/<slug>/` (`post.json` + `en.html` + `es.html`) and writes
`index.html` at the root (the Updates / Novedades index) and
`posts/<slug>/index.html`. It also reads `src/pages/<slug>/` (`page.json` +
`en.html` + `es.html` + any images) and writes a standing **project hub** at
`/<slug>/` — icon, platforms row, gallery, technical story — not dated and
not listed in Updates. **Both languages are required** — the build refuses a
post or page that has only one, deliberately: every page ships both and
`lang.js` picks one, so nobody is left without something readable.

**Bump `ASSET_VERSION` in `build-blog.py`** whenever `style.css` or `lang.js`
changes. Assets are cache-busted with `?v=N` and browsers will otherwise serve
the old one.

## The thing that will bite you

**⚠️ `cauriflores.github.io` IS A DIFFERENT REPO AND IT IS FROZEN.** It serves
Pacheco's App Store **support URL** (`/`) and the **privacy policy**
(`/privacy.html`) that Apple checks.

In App Store Connect the Support URL is a *version-level* field: changing it
requires a new app version and a full App Review of the whole app, not just the
change. Pacheco took three rejection rounds to ship. So those two pages do not
move, and nothing published here may reach them.

That is why this site exists on its own domain at all — it is not cosmetic.

Consequences in this repo:

- **Support and Privacy are linked ONLY from the Pacheco hub page**
  (`src/pages/pacheco-project/{en,es}.html`), as absolute cross-host links to
  `https://cauriflores.github.io/...`. They are Pacheco's App Store links, not
  the site's — keep them off the nav and any site-wide chrome, and do not
  "tidy" them into relative paths: a relative href would 404 here.
- `https://cauriflores.github.io/support/` links *back* here. It is not an
  orphan; keep it working.
- Nothing in this repo should ever write to `~/Developer/cauriflores.github.io`.

## `/pacheco/` is generated elsewhere

The Angular web app under `/pacheco/` is built output from the **private**
`pacheco-web` repo and copied in by `pacheco-web/tools/deploy.sh --push`, which
rsyncs `--delete` into `pacheco/` here. **Never hand-edit anything under
`pacheco/`** — the next deploy erases it.

That script used to deploy into the frozen repo and carried a guard aborting if
`index.html` or `privacy.html` had changed. The guard is gone because the script
can no longer reach those files. Do not point its `SITE=` back at the hub.

## Conventions

- The site is bilingual, English and Spanish, everywhere. New user-facing text
  needs both.
- **The prose is Cauri's to write.** Draft structure and offer it; do not put
  words in his mouth and publish them.
- `.nojekyll` is deliberate. Pages runs Jekyll by default and a failing Jekyll
  build takes the whole site down. Everything here is generated on the machine
  and committed, so publishing is a file copy that cannot fail.
- Design is Newsreader + IBM Plex Sans, CSS variables, 680px wrap.
- `style.css` and `lang.js` are **copies** of the ones on the frozen site, not
  links. They are expected to drift; that is fine.

## Deploying

Commit and push to `main`. GitHub Pages builds from the branch root. The
`CNAME` file is GitHub's — leave it alone.

DNS lives at Cloudflare. **The records must stay grey-clouded (DNS only)**;
proxying them blocks GitHub from issuing the TLS certificate, and the failure
looks like an unexplained HTTPS error hours later rather than an error at the
time.
